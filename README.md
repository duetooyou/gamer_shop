# Gamer Shop — ядро магазина цифровых товаров

Заказ из нескольких товаров, вебхук оплаты, автовыдача кодов от поставщиков,
которым нельзя доверять, и возврат денег за то, что выдать не удалось.

**Стек:** Python 3.13+ · Litestar · dishka · SQLAlchemy 2 (async, asyncpg) ·
PostgreSQL 17 · alembic · taskiq + Redis · structlog · pytest.

---

## Запуск

### Через docker compose (весь стек)

```bash
docker compose up --build
```

* API: <http://localhost:8000/api/v1> · документация: <http://localhost:8000/docs>
* Заглушки поставщиков: <http://localhost:9101>, <http://localhost:9102>
* Заглушка возвратов: <http://localhost:9201>

сами собой. Доли, лимиты и порты переопределяются переменными из

## Воспроизведение проверок

Скрипт `scripts/send_webhooks.py` эмулирует платёжную систему и служит
генератором гонок и всплесков. Заглушкам режим задаётся через `POST /_control`:
`ok | fail | timeout | dark | out_of_stock | duplicate | foreign_request_id |
lie_error | random`.

Ниже команды для локального запуска (порт 8000). Через docker compose всё то
же, адреса заглушек — `localhost:9101` и `localhost:9102`.

### Задача 1. Частичный сбой заказа

Заказ из восьми позиций, а остатка хватает не на все:

```bash
python scripts/send_webhooks.py --items STEAM-TOPUP-500:1,SUB-DISCORD-1M:7
```

```
Создано заказов: 1, первый ord_00154, сумма 3293 RUB, позиций 8
  Исходы: {'applied': 1}
  статус заказа: partially_delivered
    ord_00154-1  STEAM-TOPUP-500    delivered     код TAT9-5ZJN-G1T2
    ord_00154-2  SUB-DISCORD-1M     delivered     код BKJY-8Q79-8NHI
    ord_00154-5  SUB-DISCORD-1M     refunded      out_of_stock
    ord_00154-7  SUB-DISCORD-1M     refunded      out_of_stock
    ...
```

Шесть позиций выданы и остались у покупателя, за две вернулись деньги:

```bash
curl -s localhost:8000/api/v1/admin/orders/ord_00154/at | jq .money
#   {"paid": 3293, "delivered": 2495, "refunded": 798, "outstanding": 0}
```

`3293 = 2495 + 798`. Сумма берётся из проводок, а не из статусов, поэтому
расхождение статуса и денег спрятаться не может.

Тот же сбой посреди выдачи: убить воркер, пока позиции в `delivering`, и
поднять снова. Заказ дойдёт до `partially_delivered` сам — позиция остаётся
в `delivering`, и фоновая задача перехватывает её атомарным CAS по давности.
Автоматически это проверяет
`tests/test_partial_order.py::test_order_reaches_final_state_after_crash_mid_delivery`.

### Задача 2. Недобросовестный поставщик

Четыре способа соврать, все воспроизводятся одинаково: задать режим, оплатить
заказ, посмотреть на итог и на сверку.

**Ответил ошибкой, а код выдал.** Повтор обязан вернуть тот же код, а не
выдать второй:

```bash
curl -X POST localhost:9101/_control -H 'content-type: application/json' \
  -d '{"mode":"lie_error"}'
python scripts/send_webhooks.py --sku KEY-GTA5
#   статус delivered, ровно один код

curl -s localhost:8000/api/v1/admin/reconciliation?older_than_seconds=0 \
  | jq '{discrepancy_counts, open: (.open_discrepancies|length)}'
#   {"discrepancy_counts": {"phantom_issue": 1}, "open": 0}
```

`phantom_issue` — расхождение замечено, `open: 0` — разобрано без участия
человека. Правда установлена запросом состояния `GET /issue/{request_id}`,
код найден и отдан позиции.

**Отдал чужой код, уже уехавший другому заказу:**

```bash
curl -X POST localhost:9101/_control -H 'content-type: application/json' \
  -d '{"mode":"duplicate"}'
python scripts/send_webhooks.py --sku KEY-GTA5
#   код занят -> обращение помечено непригодным -> позиция уходит к резервному
#   discrepancy_counts: {"duplicate_code": 1}
```

**Подписан ответ чужим request_id** (`{"mode":"foreign_request_id"}`) — ответ
отбрасывается, состояние выясняется отдельным запросом, кладётся
`foreign_response`.

**Замолчал, успев выдать код** (`{"mode":"timeout"}`) — заказ остаётся в
`delivering`, фолбэк запрещён, деньги не тронуты; повтор идёт тем же
`request_id` к тому же поставщику.

Проверить, что код не уехал дважды, можно у самой заглушки:

```bash
curl -s localhost:9101/_stats | jq '{issued_count, distinct_codes, truth_count}'
#   issued_count == distinct_codes: один код в одни руки
```

`truth` — журнал того, что заглушка выдала на самом деле, включая то, о чём
соврала. Его же отдаёт `GET /issue/{request_id}`.

### Задача 3. Всплеск и лимит поставщика

Тридцать заказов оплачены разом, поставщик принимает 240 обращений в минуту:

```bash
curl -X POST localhost:8000/api/v1/admin/stock/KEY-GTA5/refill \
  -H 'content-type: application/json' -d '{"count":60}'
python scripts/send_webhooks.py --sku KEY-GTA5 --orders 30 --wait 15
```


```bash
curl -s localhost:9101/_stats | jq '{rate_limit_per_minute, over_limit, peak_per_minute}'
#   {"rate_limit_per_minute": 240, "over_limit": 0, "peak_per_minute": 35}
```

`over_limit: 0` — ни одного 429. Чтобы убедиться, что счётчик вообще умеет
расти, есть обратная проверка: тест
`test_without_the_bucket_the_supplier_limit_is_broken` снимает учёт с
магазина и получает превышение немедленно.

Прогресс виден в любой момент, в том числе посреди всплеска:

```bash
curl -s localhost:8000/api/v1/admin/progress | jq
```

```json
{
  "orders_total": 31, "orders_in_queue": 4, "orders_settled": 27,
  "items_delivered": 27, "items_refunded": 0, "items_in_queue": 4,
  "queue": [{"supplier": "a", "queued": 4, "ready": 4, "in_flight": 1,
             "oldest_wait_seconds": 6.4}],
  "rate_limits": [{"supplier": "a", "capacity": 5, "pace_per_minute": 162,
                   "available": 0.3, "granted": 35, "throttled": 92}],
  "dead_commands": 0
}
```

Неоплаченный заказ в этой очереди не стоит вовсе: команда выдачи ставится в
той же транзакции, что и подтверждение оплаты. Оплаченное обслуживается
раньше неоплаченного по построению, а не по смягчающему правилу.

### Задача 4. Картина на любой прошлый момент

Спросить можно и датой, и моментом. Дата — это не момент, а сутки, поэтому
она разворачивается в границу: `as_of` и `to` берут конец дня, `from` —
начало. Без зоны считается UTC, без `as_of` ответ будет про «сейчас».

```bash
# как было вчера — заказа ещё не существовало
curl -s "localhost:8000/api/v1/admin/orders/ord_00154/at?as_of=2026-09-09" | jq
#   {"exists": false, ...} — это ответ, а не 404

# как было по итогам десятого сентября
curl -s "localhost:8000/api/v1/admin/orders/ord_00154/at?as_of=2026-09-10" \
  | jq '{status, money}'
#   status: "partially_delivered"
#   money:  {"paid": 3293, "delivered": 2495, "refunded": 798, "outstanding": 0}

# а вот момент посреди выдачи: часть позиций уже выдана, часть ещё нет
curl -s "localhost:8000/api/v1/admin/orders/ord_00154/at?as_of=2026-09-10T16:30:11Z" \
  | jq '{status, money}'
#   status: "delivering"
#   money:  {"paid": 3293, "delivered": 899, "refunded": 0, "outstanding": 2394}

# со всей историей переходов
curl -s "localhost:8000/api/v1/admin/orders/ord_00154/at?with_events=true" | jq .events
```

`outstanding` — деньги, которые пришли, а товаром ещё не стали и покупателю
не вернулись. Посреди выдачи их 2394, к концу — ноль: обязательство
разошлось на выданное и возвращённое.

Переписать историю нельзя — это ограничение базы, а не обещание приложения:

```bash
psql -h localhost -p 5434 -U postgres gamer_shop \
  -c "UPDATE order_events SET to_status = 'delivered'"
#   ERROR:  order_events только дополняется: UPDATE запрещён
```

Итоги за период считаются из тех же журналов:

```bash
curl -s "localhost:8000/api/v1/admin/period-totals?from=2026-09-10&to=2026-09-10" | jq
```

```json
{"paid": 59700, "delivered": 59700, "refunded": 0,
 "opening_outstanding": 0, "closing_outstanding": 0, "outstanding_change": 0,
 "balanced": true, "orders_created": 30, "items_delivered": 30}
```

`balanced` — не отдельная проверка, а тождество двойной записи:
`оплачено = выдано + возвращено + прирост обязательства`. Период, разрезанный
надвое, даёт ту же сумму — проводка не может попасть в оба куска или ни в
один, потому что время проводки это `now()`, время начала транзакции.

### Как проверить, что деньги сходятся

Три независимых способа, от частного к общему.

**По одному заказу** — из проводок:

```bash
curl -s localhost:8000/api/v1/admin/orders/<id>/at | jq .money
#   paid == delivered + refunded, outstanding == 0 у закрытого заказа
```

**По всем заказам сразу** — сверка:

```bash
curl -s "localhost:8000/api/v1/admin/reconciliation?older_than_seconds=0" | jq \
  '{ledger_is_balanced, money_mismatch: (.money_mismatch|length),
    open_discrepancies: (.open_discrepancies|length),
    dead: (.dead_commands|length), stock_drift}'
#   {"ledger_is_balanced": true, "money_mismatch": 0,
#    "open_discrepancies": 0, "dead": 0, "stock_drift": []}
```

`ledger_is_balanced` — сумма дебетов минус сумма кредитов по всем счетам,
тождественный ноль. `money_mismatch` — заказы, у которых оплачено не равно
выданному плюс возвращённому; в норме список пуст.

**За период** — `/admin/period-totals` с полем `balanced`, см. выше.

Автоматически то же самое проверяют
`tests/test_partial_order.py::test_money_always_reconciles_in_the_report`,
`tests/test_ledger_reconciliation.py` и `tests/test_history.py`.

## Как это устроено

### Идемпотентность вебхука

`INSERT INTO payment_events ... ON CONFLICT (event_id) DO NOTHING RETURNING`.
Проверка «а был ли уже такой event_id» с последующей вставкой оставляет окно
гонки между SELECT и INSERT; у `ON CONFLICT` его нет. Ноль вставленных строк —
дубль, отвечаем 200 и выходим.

### Единица выдачи — позиция, а не заказ

Две одинаковые единицы товара дают две строки в `order_items`, а не поле
«количество». Так «один код на позицию» выполняется по построению, без
счётчиков: `UNIQUE(deliveries.order_item_id)` — и всё.

Позиции идут к разным поставщикам и завершаются независимо. Статус заказа —
проекция статусов его позиций: заказ закрывается, когда каждая позиция дошла
до терминального состояния, и получает `delivered`, `partially_delivered`
либо `refunded` в зависимости от того, чем это кончилось.

### Однократная выдача: три рубежа

Каждый самодостаточен, любой в одиночку не даёт задвоиться.

1. `SELECT ... FOR UPDATE` по заказу сериализует вебхуки с разными `event_id` —
   это превращает 50 одновременных «оплачено» в один переход.
2. Условный `UPDATE ... WHERE status IN (...)` вместо чтения-изменения-записи:
   переход выполняет ровно один вызов, остальные получают `rowcount = 0`.
   Он же мьютекс на выдачу — переход `paid → delivering` выигрывает один воркер.
3. `UNIQUE(deliveries.order_item_id)` и `UNIQUE(deliveries.code)` — последний
   рубеж на уровне БД. Даже при полном отказе логики вторая выдача по позиции
   и повторное использование ключа физически не запишутся.

### Ответу поставщика веры нет


| Исход | Когда | Фолбэк на B |
|---|---|---|
| `OK` | 200 с кодом, подписанный тем же `request_id` | — |
| `REFUSED` | соединение не установилось, 429 | разрешён |
| `UNKNOWN` | всё остальное, включая 5xx и «чужой» ответ | запрещён до запроса состояния |

Единственный способ отличить «не выдал» от «выдал и соврал» —
`GET /issue/{request_id}`, запрос состояния, а не новая выдача. Он же
единственный выход из `UNKNOWN`. `request_id` выводится из позиции и
поставщика, а не из номера попытки: иначе повтор попал бы в новый
идентификатор и поставщик выдал бы второй код.

Расхождения не логируются, а хранятся: `supplier_discrepancies` со
состоянием `open`/`resolved`. Строка в `open` — работа, которую кто-то обязан
доделать. Разбор идёт там же, где обнаружение, поэтому в норме открытых нет,
а `discrepancy_counts` показывает, сколько всего случилось каждого вида.

### Журнал денег

Двойная запись, обе строки вставляются одним запросом:

| Событие | Дебет | Кредит |
|---|---|---|
| оплата подтверждена | `cash_in` | `customer_liability` |
| позиция выдана | `customer_liability` | `revenue` |
| возврат начислен | `customer_liability` | `refund_payable` |
| возврат отправлен | `refund_payable` | `cash_out` |

Отсюда `SUM(debit) − SUM(credit) ≡ 0`, а остаток по `customer_liability` и
есть «оплачено, но ещё не разрешилось» — журнал сам является отчётом сверки.
Повтор гасится уникальным `idempotency_key`. Деньги — целые числа в рублях,
как в контракте вебхука.

### Аутбокс: команда и её причина в одной транзакции

Выдача, возврат и расчёт заказа ставятся командами в таблицу `outbox` — в той
же транзакции, что и изменение состояния, которое их породило. Взятие в
работу это не блокировка, а аренда: команда прячется на `lease_seconds` и
всплывает сама, если исполнитель умер, не отчитавшись. Потерять её нельзя,
а выполниться она может дважды — поэтому каждый обработчик идемпотентен.

Исчерпавшая попытки команда не удаляется, а уходит в `dead` и попадает в
сверку: иначе «ничего не теряется» превратилось бы в слова.

### Лимит поставщика: ведро токенов в базе

Лимит у поставщика один на всех, а процессов несколько — API, воркеры,
планировщик. Поэтому учёт живёт не в памяти, а строкой в
`supplier_rate_limits`, и выдача разрешения умещается в один `UPDATE` с
условием: под READ COMMITTED второй `UPDATE`, дождавшись блокировки, заново
перечитывает строку и перепроверяет условие, так что два воркера не выдадут
одно разрешение дважды. Токены не доливает фоновый тик — они начисляются в
момент обращения, исходя из времени с прошлого.

Разрешение берётся **до** заявки на выдачу, а не перед самим запросом.
Позиция, уже переведённая в `delivering`, упершись в лимит, застряла бы там
до фонового перехвата, и всплеск растянулся бы на минуты вместо секунд.

Релей смотрит на остаток разрешений, прежде чем брать работу: сколько у
поставщика осталось токенов, столько команд к нему и уедет. Остальные ждут в
очереди нетронутыми, а сам релей заходит снова через `poll_interval`, не
дожидаясь планового тика. Упереться в лимит — не попытка: счётчик попыток
возвращается обратно, иначе всплеск сам себя добил бы до `dead`.

Пачка делится по партициям поровну: очередь к одному поставщику не должна
съедать её целиком, иначе расчёты и возвраты будут ждать выдач.

**Почему магазин идёт медленнее объявленного лимита.** Своё ведро он
опустошает в момент, когда только собирается послать запрос, а поставщик —
когда запрос до него дошёл. На одинаковых числах оба ведра идут ноздря в
ноздрю, и любое дрожание сетевой задержки выносит за лимит: наш пятый токен
появляется на те же миллисекунды раньше, чем его. Отсюда
`SUPPLIER_RATE_LIMIT_SAFETY` — доля от объявленного лимита, с которой мы
идём, и требование держать всплеск строго меньше того, что стерпит
поставщик. Это не перестраховка, а плата за то, что часы у нас разные.

### Журнал состояний: почему триггер, а не приложение

Состояние заказа хранится перезаписью, поэтому «как было» из таблиц не
достать. Достаётся из `order_events` — журнала, который только дописывается.

Пишет его триггер, а не код. Приложение, которое ведёт журнал само, рано или
поздно забывает сделать это в одной ветке из десяти, и восстановленная
картина начинает врать; триггер же не пропустит перехода, откуда бы тот ни
пришёл — хоть из ручного `UPDATE` в консоли. Дополнение защищено тем же
способом: `UPDATE` и `DELETE` по журналу и по проводкам денег запрещены
триггером.

Время события — `now()`, то есть время начала транзакции, как и у проводок.
Поэтому срез «на момент» никогда не разрежет транзакцию пополам: либо видно
всё, что она сделала, либо ничего. Самого кода в журнале нет: журнал читают
широко, а код — это товар.

### Выдача идёт тремя фазами

Заявка (короткая транзакция) → поход к поставщику (без транзакции) → фиксация
(короткая транзакция). Держать блокировку строки на время HTTP-запроса,
который может зависнуть на десятки секунд, нельзя — это заблокировало бы и
вебхуки, и сверку по этому заказу. Крах воркера между фазами не теряет
позицию: она остаётся в `delivering`, и фоновая задача перехватывает её
атомарным CAS по давности.

### Витрина под нагрузкой

Остаток лежит счётчиком в отдельной узкой таблице `product_stock`, а не
считается `COUNT(*)` по ключам: O(1) вместо скана, обновляется в той же
транзакции, что и резерв, поэтому не расходится.

Запрос идёт по покрывающему частичному индексу
`products(type, sku) INCLUDE (name, price, currency) WHERE is_active` —
Index Only Scan без обращений к таблице, снятые с продажи товары в индексе не
хранятся вовсе. Пагинация keyset по `sku`, а не `OFFSET`: время не зависит от
глубины страницы.

Страница сначала отбирается подзапросом с `LIMIT`, и только потом к готовым 50
строкам подтягивается остаток по первичному ключу. Если писать плоский `JOIN`,
планировщик на больших объёмах уходит в merge join и вычитывает десятки тысяч
строк остатков ради полусотни нужных. На 205 тыс. SKU: 0.9 мс против 245 мс у
плоского join и 662 мс у варианта с `OFFSET`.

## Масштабирование

* **Вебхуки.** `FOR UPDATE` держится микросекунды и блокирует один заказ, так
  что API масштабируется репликами. `payment_events`, `ledger_entries` и
  `order_events` растут безгранично — партиционировать по месяцам, старые
  партиции в архив. Журналы для этого удобны тем, что запросы к ним всегда
  ограничены по времени.
* **Выдача.** Воркеры независимы: право на позицию берётся условным UPDATE, а
  не координатором. Дальше — отдельные очереди на поставщика (партиции в
  аутбоксе уже есть) и circuit breaker, чтобы медленный поставщик не выедал
  весь пул.
* **Лимит.** Строка ведра — точка сериализации на поставщика. При десятках
  тысяч обращений в минуту она станет горячей: тогда либо ведро в Redis с
  Lua-скриптом, либо шардирование ведра на N строк с долей лимита в каждой.
  Пока лимиты измеряются сотнями в минуту, строки в Postgres достаточно, и
  она не требует второго хранилища с собственными отказами.
* **Прогресс.** `/admin/progress` считает `COUNT(*)` по `order_items` — на
  миллионах строк это станет заметно. Лечится счётчиками, обновляемыми тем же
  триггером, что пишет журнал.
* **Витрина.** Выносится на реплику для чтения, остаток кэшируется с коротким
  TTL, карточки — надолго. При росте до миллионов SKU — партиционирование
  `products` по типу.
